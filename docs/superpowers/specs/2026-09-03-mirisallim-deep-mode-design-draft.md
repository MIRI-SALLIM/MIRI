사용자 추가 확인(2026-09-03): 로그인은 카카오를 사용한다. 라이트는 미니게임·재미로 보는 심리테스트 같은 경험이고, 딥은 사이트의 정체성을 담는 핵심 경험이다. 이 확인은 제품 방향과 로그인 수단에 대한 결정이며, 아래 모든 세부 제안이나 구현·배포에 대한 일괄 승인은 아니다.

분석 자료:

## 2. 정체성에서 도출하는 제품 결정

핵심 목적은 재무 우열이나 결혼 적합성 판정이 아니라, 숫자를 근거로 어려운 대화를 시작하고 두 사람이 자신의 기준을 정하도록 돕는 것이다.

라이트와 딥은 단순한 난이도 차이가 아니라 사용자에게 주는 경험이 다르다. 라이트는 "서로 얼마나 알고 있는지 재미로 알아보기", 딥은 "꺼내기 어려운 돈 이야기를 시작하고 함께 살 기준 정하기"다. 라이트의 재미와 공유성을 유지하되 검증된 심리검사라고 표현하지 않는다. 딥에서는 점수 경쟁이나 놀라운 폭로보다 정확한 입력, 안전한 공동 공개, 대화를 이어갈 결과를 우선한다.

따라서 라이트는 딥의 축소판이나 필수 체험판으로 만들지 않는다. 브랜드의 핵심 설명은 딥이 제공하는 가치에 두고, 라이트는 독립적으로 즐기거나 부담 없이 서비스를 접할 수 있는 선택지로 둔다. 딥의 질문 수를 늘리는 것만으로 깊이를 만들지 않고, 응답의 이유·현실적 제약·조정 가능한 조건까지 연결한다.

| 항목 | 이번 설계 기준 |
|---|---|
| 로그인 | 딥은 카카오 로그인 필수. 초대 코드는 로그인 대체 수단이 아니다. 라이트의 기존 익명 참여는 유지한다. |
| 라이트와 관계 | 독립 진입점을 유지한다. 라이트 완주를 딥의 선행 조건으로 만들지 않는다. |
| 상대 예측 | 라이트에 남긴다. 딥 입력에 guesses/partnerPredictions를 추가하지 않는다. |
| 결과 공개 | 양측 제출·공동 계획 확인·공개 동의가 모두 충족된 뒤 공동 결과를 연다. |
| 개인 선공개 | 이전 제안에서 제외한다. 기다리는 동안 자기 입력의 확인·오류 안내만 제공한다. |
| 결과 중심 | 공동 현금흐름 → 대화 주제 최대 3개 → 합의 초안 → 다음 점검. |
| 통계 | 해당 지표 옆의 참고 정보. 등수·궁합 점수·결혼 판정을 만들지 않는다. |
| 합의 | 제안, 보류, 상호 확인을 구별한다. 합의를 강요하거나 법적 효력을 암시하지 않는다. |
| 문구 | 관찰 → 맥락 확인 → 열린 질문. 상대를 비난하거나 개인정보 공개를 압박하지 않는다. |

## 3. 자료 분석: 유지할 것과 바로잡을 것

### 3.1 변경 사실

- 새 JSON은 구버전 대비 D9(investment), D10(debt)을 추가하여 8→10문항이 되었다.
- `sayDoGap`, `valueGapWeights`, `typeAxis`, `inputValidation`은 구버전과 내용이 동일하다.
- 저장소의 `apps/backend/config/parameters.json`은 아직 8문항이다.
- 저장소 질문에는 `left`/`right`가 있지만 첨부 JSON에는 없다. 단순 교체하면 현 질문 API가 일반적인 대체 라벨을 사용한다.

### 3.2 구현 전에 처리할 문제

| 문제 | 근거·영향 | 제안 |
|---|---|---|
| D5와 D9의 방향 불일치 | 두 문항에서 모두 안전 쪽인 5를 선택해도 현재 정규화는 1과 5가 되어 평균 3이다. | 높은 값=안전 선호라면 D5 reverse를 false로 바꾸고 D9는 false 유지. 투자 실제값의 방향도 별도로 검토한다. |
| 역채점과 격차의 구별 | 양쪽 답에 같은 역채점을 적용한 절댓값 차이는 원래 차이와 같다. | D5 문제를 모든 커플 격차가 틀렸다는 뜻으로 과장하지 않는다. 개인 성향 평균·의향/현황 비교에 특히 영향을 준다. |
| 단위가 전부 원/월로 표기됨 | 예금·보증금·부채 잔액을 12로 나누면 잘못된 계산이다. | 잔액=원, 월 흐름=원/월, 연 흐름=원/년, 비율=소수로 분리한다. |
| 개인 정보와 공동 계획 혼재 | 한 사람이 입력한 isHomeless가 상대의 사실까지 대신 확정한다. | 주택 보유 등 개인 사실은 각자 입력. 공동 주거 계획은 한 번 작성하되 양쪽이 동일 버전을 확인한다. |
| 부채 종류로 상환 방식 추정 | 대출 종류만으로 실제 계약의 상환 방식을 확정할 수 없다. | 직접 입력한 월 상환액 우선. 추정 시 실제 repaymentType을 질문하며 모르면 산출 불가로 남긴다. |
| 상여·주거·공동비 중복 위험 | 월 평균 소득에 이미 포함한 상여, 두 사람이 동일하게 입력한 공동비 등이 합산될 수 있다. | 상여 포함 여부, 각자의 실제 부담분, 현재 주거비와 새 주거비를 구별한다. |
| 전체 자산과 당장 쓸 돈 혼재 | 보증금·청약·투자자산 전체를 즉시 쓸 수 있는 결혼자금으로 취급할 수 없다. | 보유액, 실제 투입 예정액, 사용 가능 시점을 별도로 받는다. |
| Say-Do가 실측으로 표현됨 | 자기보고와 추정 잉여자금은 관찰된 거래내역이 아니다. | 첫 출시는 의향과 입력 현황의 병렬 설명만 제공. 숫자형 불일치 판정은 보류한다. |
| 통계 앵커의 한계 | 평균 성격 지표, 중앙값끼리의 비율, 전체 가구 투자비중을 개인 또래 중앙값처럼 사용한다. | 모집단·분자/분모·기간을 재검증하고 맞지 않으면 비교를 생략한다. |
| 문항 수=표본 수라는 동률 설명 | 추가 후에는 모든 영역이 2문항이며, 문항 수는 통계적 표본 수가 아니다. | 6절의 결정적 정렬 규칙을 적용하고 신뢰도가 높다는 설명을 하지 않는다. |
| 파이프라인 문서의 잔존 표현 | 8문항/8영역 표현, F-40에 정책·자금 갭이 혼재한다. | 딥은 5영역·10문항으로 통일. 내부 기능 이름은 cashflow, fundingGap, policyMatch처럼 분리한다. |
| 저축액 비교가 부모 지원을 배제한다는 주장 | 저축 잔액 자체에도 가족 지원이 포함될 수 있다. | 자금 출처를 알 수 없으면 자력 축적이나 노력의 차이로 해석하지 않는다. |
| 정책 요건의 일반화 | 청약통장, 무주택, 혼인 날짜 등이 모든 정책에서 동일하게 작동한다는 보장이 없다. | 검증된 정책별 요건만 적용. 추정 세전소득으로 자격을 확정하지 않는다. |

`D=declared/5`를 향후 유지할 경우 1이 0.2가 되는 문제도 있다. 0~1 변환 의도라면 `(normalizedAnswer-1)/4`가 일관된다. 다만 척도를 맞추는 것만으로 의향과 재무 상태가 같은 개념이 되지는 않는다.

## 4. 권장 범위와 사용자 여정

### 4.1 접근 방식

권장: 선택·금액 입력 중심의 구조화된 대화와 규칙 기반 후속 질문. 재현 가능한 계산·템플릿을 기본으로 하고 LLM은 후속 선택 기능으로 둔다.

대안인 긴 설문은 구현이 쉽지만 이유를 놓치기 쉽다. 자유 AI 상담은 유연하지만 필수 데이터 누락, 비용, 민감정보 전송과 잘못된 설명의 위험이 있다. 첫 출시에는 권장안을 사용한다.

### 4.2 작성 흐름

| 순서 | 사용자 경험 | 저장·처리 |
|---|---|---|
| 1 | 딥 설명을 보고 로그인한다. | account identity와 앱 로그인 세션 |
| 2 | 생성 또는 초대로 커플 진단에 참여한다. | 계정 2개와 진단 세션 연결. 동일 계정의 양쪽 참여 금지 |
| 3 | 공개 범위·보관 안내를 확인한다. | consentVersion, 이후 최종 제출에서 재확인 |
| 4 | 공동 계획을 한 사람이 제안한다. | sharedPlan 초안. 상대가 이미 동의했다는 표시 금지 |
| 5 | 각자 소득→지출→부채→자산을 입력한다. | 본인 전용 자동저장. 빈 값과 0 구별 |
| 6 | 10문항에 답하고 중요한 대화 주제 최대 2개를 고른다. | questionId별 답, 중요 주제 |
| 7 | 필요한 경우 이유·예외 조건을 짧게 답한다. | 별도 맥락 데이터. 성향 점수에 몰래 반영하지 않음 |
| 8 | 공유될 정보와 공동 계획 버전을 확인하고 제출한다. | inputRevision, planVersion, consentVersion 고정 |
| 9 | 상대를 기다린다. | 완료 여부만 반환. 상대 숫자·답·예상 결과 없음 |
| 10 | 두 사람의 결과와 대화 카드를 연다. | 같은 분석 스냅샷, 권한에 맞는 응답 |
| 11 | 주제를 이야기하고 합의·보류·다음 점검을 남긴다. | 버전 있는 agreement |

15분은 개인별 핵심 작성의 UX 목표이며 보장 시간이 아니다. 대출 건수·정보 확인 시간과 공동 대화 시간은 별도다. 진행률은 현재 적용되는 질문 기준으로 계산한다.

| 가치관 | D1~D10: value 1..5 또는 명시적 skipped | ID 기반 저장. skipped를 3점으로 바꾸지 않음 |
| 대화 맥락 | 이유 선택, 짧은 메모, 중요 주제 | 메모 선택 입력, 300자 제한 제안. 제3자 이름·계좌정보 입력을 요구하지 않음 |

정책 기능이 없는 초기 버전에서 고용 형태·정확한 혼인신고일·청약 가입기간·정확한 생년월일을 무조건 수집하지 않는다. 통계 비교에 연령대 등이 필요하면 목적을 설명하고 선택적으로 받는다. 정책 모듈이 준비된 뒤 해당 정책의 필요 필드만 추가한다.

부채는 최초 한 건만 표시하고 필요할 때 추가한다. 첫 버전의 API 상한은 개인별 30건으로 제안한다. 초과 시 명시적으로 알리며, 서로 다른 대출을 자동으로 합치거나 누락하지 않는다. 이 수치는 금융 판단 기준이 아니라 요청 크기 제한이다.

### 4.4 기본 질문과 후속 대화

기본 D1~D10의 ID와 주제는 새 JSON을 기준으로 유지한다. 좌우 라벨을 명시 필드로 분리하며 D5 방향 수정은 검토 후 새 버전에 반영한다. 질문별 의미를 다음처럼 구분한다.

| 영역/문항 | 관찰 대상 | 조건부 후속 질문 | 결과에서 할 일 |
|---|---|---|---|
| 저축 D1·D2 | 선저축 여부·목표 계획성 | "매달 지키고 싶은 저축액은? 줄여야 할 때 무엇부터 조정할까요?" | 각자 원하는 수준과 입력상 여력을 함께 놓고 목표 논의 |
| 소비 D3·D4 | 구매 의사결정·관계 지출 우선순위 | "경조사비는 개인비와 공동비 중 어디에서 내고 싶나요?" | 선물 규모를 절제/낭비로 평가하지 않고 예산 범주 결정 |
| 투자 D5·D9 | 위험 선호·여유자금 배치 | "이 돈을 언제 쓸 예정인가요? 사용 시점에 손실이 있어도 괜찮나요?" | 목적·기간 차이를 대화. 특정 상품이나 수익률 추천 안 함 |
| 부채 D6·D10 | 대출 태도·조달 방식 | "대출을 고려할 수 있는 목적과 피하고 싶은 상황은 무엇인가요?" | 대출 거부/선호가 취향인지 제약인지 구별 |
| 공동관리 D7·D8 | 자금 통합·정보 공개 기대 | "공동비만 공유한다면 개인 지출은 총액과 내역 중 어디까지 공유할까요?" | 생활비 분담·자유지출·공개 범위 합의 |

후속 답변은 기본 10문항의 영역 평균에 합산하지 않는다. 입력 중 다른 사람의 답을 근거로 질문을 바꾸지 않는다. 양측 공개 후에는 차이가 있는 항목을 근거로 공동 대화 질문을 제시할 수 있다.

## 5. 데이터·인증·공동 공개 설계

### 5.1 저장 경계

- `users`: 로그인 제공자의 고유 식별자와 내부 userId. 이메일 주소 일치만으로 계정을 자동 병합하지 않는다.
- `auth_sessions`: 서버 측 로그인 세션, 만료, 폐기 상태. 브라우저에는 HttpOnly 쿠키 사용.
- `deep_sessions`: 두 계정, round, 버전들, 상태, sharedPlan, 각자의 제출·공개 동의·입력 스냅샷, expiresAt. 첫 버전은 제한된 크기의 세션 문서에 묶어 최종 제출과 공개 전환을 원자적으로 검사한다.
- `deep_reports`: 결정적 분석 스냅샷, 입력 버전·계산 버전·공개 범위. 세션 상태를 확인한 뒤에만 반환한다.
- `deep_agreements`: 주제, 제안문, 버전, 각자 확인 시각, 보류 이유, 다음 점검일.

API용 private input / waiting / ready DTO를 구분한다. MongoDB 문서를 통째로 API에 직렬화하지 않는다.

각 금액은 값 외에 `status(known/unknown/withheld)`, `precision(exact/estimate)`, `source(self_reported/calculated)`, 기준 시점을 기록한다. 돈의 단위는 필드 스키마에서 고정한다. 미입력과 모름은 서버의 초안 상태에서 구별하며, zero는 유효한 숫자다.

source와 계산 버전은 서버가 지정한다. 클라이언트가 자기보고 값을 calculated나 검증된 값으로 바꿀 수 없게 한다.

### 5.2 공개 조건

공동 결과 공개에는 다음이 모두 필요하다.

1. 서로 다른 두 계정이 현재 round에 참여했다.
2. 두 사람이 각자의 현재 입력 revision을 제출했다.
3. 두 사람이 같은 sharedPlanVersion을 확인했다.
4. 두 사람이 해당 결과 공개 범위와 consentVersion에 동의했다.
5. 세션이 닫히거나 만료되지 않았다.

개별 raw 금액을 숨겨도 합산금액에서 상대 금액을 역산할 수 있다. 합산 분석 포함 자체를 공개 동의 대상에 넣는다. 동의하지 않은 값은 파생 결과·대화 카드·LLM 입력에서도 제외한다. 필수 금액이 비공개면 해당 계산은 unavailable로 반환하고, 허용된 가치관 대화만 제공할 수 있다.

공동 계획은 처음부터 공동 공개 문서임을 표시한다. 상대의 비공개 입력을 공동 계획에 자동 채우지 않는다. 계획 수정 시 version을 올리고 기존 계획 확인은 무효화한다. 한 명이라도 제출한 round는 계획과 제출 입력을 잠근다. 수정은 새 round를 만들고 양측 확인·동의를 다시 받는다.

공개 조건 통과는 단일 문서 조건부 갱신으로 고정한다. 결과 캐시는 sessionId/round/inputRevisions/planVersion/questionVersion/ruleVersion/consentVersion 조합에 종속시킨다. 캐시 유무와 관계없이 매 요청에서 계정·멤버십·만료·동의를 검사한다.

### 5.3 보관·철회 제안

- 초안 30일, 결과·합의 90일을 초기 제안값으로 두며 사용자 검토 후 확정한다. 기존 Light 7일 TTL은 변경하지 않는다.
- 만료·연결 해제·공동 공개 동의 철회 시 공동 결과의 이후 조회를 즉시 차단하고 파생 캐시도 폐기한다.
- 계정 삭제는 해당 사용자의 재무 입력을 삭제하고 연결된 공동 결과를 폐기한다. 상대의 독립적인 개인 계정 데이터까지 임의 삭제하지 않는다.
- TTL은 물리 정리를 위한 장치이며, 만료 접근 차단은 API에서 즉시 수행한다. 별도 컬렉션의 결과·합의도 수명과 삭제를 연동한다.
- 다운로드되거나 상대가 이미 본 내용을 되돌릴 수는 없음을 안내한다. MVP에는 민감 재무 PDF·공개 URL 공유를 넣지 않는다.
- 로그·에러·일반 분석 이벤트에서 토큰, 입력 본문, 금융 금액, 대화 원문을 제외한다. 비밀값은 플랫폼 환경 변수에만 둔다.

## 6. 계산·우선순위·설명 파이프라인

### 6.1 단위와 현금흐름

화면에서 만원 단위를 쓰더라도 API에는 원 단위 정수를 전송한다. 잔액과 기간 흐름을 별도 필드로 표현하고, 금리는 연이율 소수(예: 0.04), 비율은 소수, 기간은 개월 정수로 통일한다. 반올림은 출력에서 수행한다.

기본 계산은 서로 구분한다.

- 정기 월 소득 = 두 사람의 월 실수령 합계.
- 연평균 환산 월 소득 = 정기 월 소득 + 월 입력에 미포함된 세후 연 상여 합계 / 12. 보너스를 매달 실제 입금되는 돈처럼 그리지 않는다.
- 예상 잉여자금 = 해당 소득 − 비주거 고정비 − 시나리오 생활비 − 시나리오 주거 운영비/월세 − 유지되는 기존 대출 상환 − 신규 주거대출 상환.
- 초기 필요자금 = 보증금/자기자본/사용자가 입력한 일회성 비용. 월 생활비와 별도 표시한다.
- 목표 부족액 = 목표금액 − 중복 배정 없이 확보된 목표 전용 자금. 목표기간이 지났거나 월 적립여력이 0 이하이면 도달일을 억지 계산하지 않는다.

`0.85`는 합가 시나리오의 추정 기본값일 뿐이다. 현재 별거·비주거 변동지출에만 적용하고 이미 합가한 가구에는 기본 1.0을 사용한다. 사용자가 계획 예산을 직접 조정할 수 있게 한다. 카테고리별 절감계수와 전체 0.85를 이중 적용하지 않는다.

주거대출은 지출 위치가 한 곳뿐이어야 한다. housingCost는 월세·관리·공과금 등 대출 제외 운영비이며 대출 상환은 debtPayments에만 포함한다. 보증금 반환·기존 대출 상환·새 대출 조달은 초기 자금표에서 상계한다.

월 상환액을 아는 대출은 현금흐름에 그 값을 우선 사용한다. 금리와 상환 방식이 없으면 미래 잔액·이자 변화 시뮬레이션은 제공하지 않는다. 만기일시 대출은 월 이자와 만기 원금 부담을 구분한다. 원금균등은 회차별 계산하며 단일 값 표시 시 기준 회차를 명시한다.

월 소득이 0이면 해당 비율은 unavailable로 반환한다. 음수 잉여자금·순자산은 숨기거나 0으로 바꾸지 않는다. 표시 금액의 범위를 임의로 눌러 원래 값을 왜곡하지 않는다.

### 6.2 가치관 차이와 상위 주제

- 문항 차이: 양측 답이 있을 때 `abs(a-b)/4`.
- 영역 차이: 그 영역의 유효 문항 차이 평균. 두 문항 모두 비교 가능할 때 complete, 한 문항이면 partial.
- 문항별 결과를 보존한다. D3 구매속도와 D4 관계지출을 하나의 절제성으로 설명하지 않는다.
- 처음에는 complete 영역을 상위 주제 후보로 삼는다. partial은 별도 설명 가능하되 완전한 영역 점수처럼 비교하지 않는다.
- 정렬: 차이 내림차순 → 양측이 중요 주제로 선택한 수 내림차순 → 고정 순서(공동관리, 저축, 소비, 부채, 투자).
- 마지막 고정 순서는 재현성을 위한 제품 규칙이며 과학적 중요도 순위가 아니다.
- 0보다 큰 차이가 있는 영역에서 최대 3개만 선택한다. 차이가 없으면 갈등을 만들지 않고 공통 기준을 보여준다.
- 전체 0.2 가중 평균은 실험·내부 검토 용도에 한정하고 궁합 점수로 노출하지 않는다.

### 6.3 의향과 현재 여건

첫 출시에서 숫자형 Say-Do 판정과 threshold 0.4 기반 경고를 비활성화한다는 제안이다. 가치관과 자기보고 현황을 나란히 보여주되 원인·불성실함·거짓말을 추론하지 않는다.

예시: "저축을 먼저 배정하고 싶다고 답했어요. 입력한 고정비와 상환액을 반영하면 현재 남는 금액은 이 정도예요. 유지하고 싶은 저축액과 조정할 수 있는 지출을 함께 정해볼까요?"

향후 숫자형 기능은 비교 개념·방향·단위·대상 집단·근거를 정리한 뒤 별도 승인을 받는다. 금융자산 비중을 투자 능력이나 위험 감당 능력으로 등치하지 않는다.

### 6.4 통계와 정책

- benchmarks는 허용된 지표 경로 목록과 단위 레지스트리를 통해 읽는다. 전체 설정을 보고서에 그대로 노출하지 않는다.
- 같은 소득 정의·기간·모집단이 아닐 때 해당 참고선을 생략한다. 여러 통계의 주변 분포를 결합해 가상의 맞춤 백분위를 만들지 않는다.
- 자기보고 월 상환액/실수령액은 "실수령 대비 상환 부담"으로 부르며 규제 DSR이나 대출 승인 가능액이라고 표시하지 않는다.
- policy 상태는 unavailable / needsInformation / candidate / noneMatched로 구별한다. 후보도 최종 자격 승인이 아니다.
- 검증된 정책 데이터가 없는 MVP는 unavailable만 반환하고 정책 전용 질문은 숨긴다. 정책·LLM 실패로 기본 리포트가 막히지 않도록 한다.

### 6.5 LLM과 비용

MVP는 템플릿으로 정상 동작한다. LLM은 나중에 별도 opt-in 설명 보조로 붙인다.

- 선택된 최대 3개 주제와 허용된 관찰·규칙 ID만 전송한다. 원문 재무입력·자유메모·전체 대화는 보내지 않는다.
- 숫자 계산·자격 판정·우선순위 선정은 서버가 수행한다.
- 출력은 observation/question/options 구조를 검증하며 입력 근거에 없는 금액·등급·판정을 허용하지 않는다.
- 같은 보고서 버전은 재생성하지 않고 캐시한다. 갱신·폴링마다 모델을 호출하지 않는다.
- 타임아웃·형식 오류·동의 없음이면 준비된 템플릿을 사용한다.

## 7. 공동 리포트와 합의의 구체적인 형태

리포트 순서는 다음과 같다.

1. **우리의 월 예산**: 정기 소득, 지출, 상환, 잉여자금과 추정 표시.
2. **지금 이야기할 주제 최대 3개**: 양쪽 응답, 입력상 맥락, 열린 질문.
3. **계획을 바꾸면 달라지는 숫자**: 사용자 조건에 따른 주거·목표 시나리오. 입력 부족이면 이유와 필요한 항목 표시.
4. **우리 기준 초안**: 공동비 분담, 각자 자유지출, 협의할 구매 금액, 저축 목표, 예외·재협의 조건.
5. **다음 대화**: 합의/보류 항목과 사용자가 정한 점검일. 자동 알림은 별도 동의와 기능이 생긴 후 제공.

정체성 문서의 유형 조합·16개 해설은 보조 콘텐츠로 해석한다. 현재 Light의 유형 축과 딥 질문의 축이 자동으로 같아지는 것은 아니며, 새 자료에도 딥 전용 유형 매핑과 16개 해설은 완성돼 있지 않다. MVP는 답변에 직접 근거한 서술형 태그(예: "공동비 분담 선호")만 제안하고, 고정된 16조합 콘텐츠는 별도 유형 규칙과 카피 검토 후 추가한다. 이를 핵심 결과보다 먼저 개발하지 않는다.

대화 카드 예시:

- 관찰: "한 분은 통합 관리를, 다른 분은 공동비만 분담하는 방식을 선호해요."
- 질문: "공동생활에 필요한 정보와 개인의 자유를 각각 어디까지 지키면 좋을까요?"
- 선택 가능한 시작점: 공동비 전용 통장 / 일정 비율 분담 / 일정 기간 시험 운영. 특정 안이 정답이라는 표시 없음.
- 기록: 각자의 의견, 합의문, 적용 시작일, 다시 이야기할 조건.

합의 상태는 proposed / agreed / deferred로 둔다. 내용이 바뀌면 version을 올리고 양측 확인을 초기화한다. 합의서의 확인은 법적 전자서명으로 표현하지 않는다. 한쪽이 계속 보류해도 정상 사용 상태다.

## 8. 백엔드 구성과 API 계약 초안

### 8.1 현재 코드와 분리 지점

현재 `main.py`는 딥 질문 조회를 제공하지만 세션 생성에서 light_questions 개수를 사용한다. `schemas.py` 입력은 Light의 0..3 배열이고, `session_repository.py` 결과는 `calculate_light_canonical_result`를 호출한다. mode 문자열만 deep으로 바꾸는 방법은 사용할 수 없다.

FastAPI·Pydantic·PyMongo Async·Atlas·Railway 구성은 유지한다. 기존 Light 서비스 전체를 리팩터링하지 않고 딥 하위 모듈과 인증을 추가한다.

| 경로(신설 제안) | 책임 |
|---|---|
| `apps/backend/auth/schemas.py`, `service.py`, `router.py`, `repository.py` | 제공자와 분리된 계정, 로그인 세션, 인증 의존성 |
| `apps/backend/deep/schemas.py`, `router.py` | 딥 전용 입력·상태·결과 계약 |
| `apps/backend/deep/repository.py`, `service.py` | 멤버십, 제출, 버전, 공동 공개, 보관 |
| `apps/backend/deep/engine/cashflow.py`, `debt.py`, `values.py`, `topics.py` | DB·HTTP와 독립된 계산 |
| `apps/backend/deep/report.py`, `agreements.py` | 공개 가능한 결과 DTO와 상호 확인 |
| `apps/backend/config/deep_questions.v2.json` | 10문항 ID·좌우 라벨·영역·역채점·설명 |
| `apps/backend/config/deep_rules.v1.json`, `deep_copy.ko.v1.json` | 단위·정렬·기능 설정 및 중립 문구 |
| `apps/backend/tests/unit/test_deep_*.py`, `tests/integration/test_deep_*.py` | 계산·계약·보안·동시성 검증 |

기존 Light용 parameters와 공개 config 계약을 새 첨부 파일로 통째로 덮어쓰지 않는다. deep-v2를 신설하고 세션에 질문·규칙·문구 버전을 고정한다. 기존 deep-v1 공개 API 및 legacy mode=deep 경로는 의존 클라이언트를 조사한 뒤 미인증 접근과 잘못된 Light 계산을 막는 전환 규칙을 적용한다.

### 8.2 계약 초안

아래는 합의를 위한 제안 API이며 아직 생성된 OpenAPI가 아니다. 프론트는 이 표를 실제 계약으로 코딩하지 않고, 구현 시 백엔드 생성 명세를 받는다.

| 메서드·경로 | 역할 |
|---|---|
| `GET /api/v1/auth/me`, `POST /api/v1/auth/logout` | 계정 확인·로그아웃. 카카오 로그인 시작/콜백은 구현 전 공식 문서와 앱 설정을 확인하여 구체화 |
| `GET /api/v1/deep/questions?version=deep-v2` | 인증 후 질문 조회 |
| `POST /api/v1/deep/sessions` | 딥 생성, 멱등성 키 |
| `POST /api/v1/deep/invitations/{code}/join` | 로그인된 다른 계정의 초대 수락 |
| `GET /api/v1/deep/sessions/{id}/me/input` | 자신의 입력 조회 |
| `PATCH /api/v1/deep/sessions/{id}/me/input` | expectedRevision을 이용한 자동 저장 |
| `GET/PATCH /api/v1/deep/sessions/{id}/plan` | 명시적으로 공유한 공동 계획 조회·제안 |
| `POST /api/v1/deep/sessions/{id}/plan/confirm` | 특정 planVersion 확인 |
| `POST /api/v1/deep/sessions/{id}/me/submit` | 입력 revision·계획 version·공개 동의 고정 |
| `GET /api/v1/deep/sessions/{id}/status` | 상대 완료 여부와 공개 준비 상태 |
| `GET /api/v1/deep/sessions/{id}/result` | waiting 또는 권한 검사를 통과한 ready DTO |
| `POST /api/v1/deep/sessions/{id}/rounds` | 수정용 새 round 제안, 이전 제출을 몰래 변경하지 않음 |
| `GET/POST /api/v1/deep/sessions/{id}/agreements` | 합의 조회·제안 |
| `POST /api/v1/deep/sessions/{id}/agreements/{agreementId}/confirm` | 현재 합의 버전 상호 확인 |
| `POST /api/v1/deep/sessions/{id}/withdraw` | 공동 공개 철회·향후 조회 차단 |

`401` 미인증, `404` 비멤버/사용 불가 리소스, `409` revision·제출·계획 충돌, `410` 본인 세션 만료, `422` 구조/범위 오류, `429` 제한, `503` 저장소 장애를 구분한다. 저소득·큰 부채·음수 잉여자금 자체는 422 사유가 아니다. 네트워크 실패한 자동 저장은 서버 성공으로 표시하지 않는다.

이 절은 의존성과 완료 기준을 정하는 개발 로드맵이다. 설계 승인 후 각 묶음을 실패 테스트 → 최소 구현 → 검증 순서의 실행 계획으로 분리한다. 아직 실행 지시가 아니다.

프로덕션은 현재 fix/gate1-openapi-contract 소스를 이번 계획 작성으로 변경하지 않는다. 실제 작업 시작 시 최신 코드와 사용자 변경을 재확인하고 작업 기준 브랜치를 정한다. 별도 시험 환경과 기능 비활성 기본값으로 검증한 뒤 배포 승인을 받는다. 추가 유료 리소스나 OAuth 앱 외부 설정을 지금 생성하지 않는다.

## 10. 구체적인 검증 사례

1. D5=5, D9=5이면 안전 지향 값이 둘 다 같은 방향이어야 한다. D5의 reverse 교정 전후에도 동일 문항의 양측 절댓값 격차는 같아야 한다.
2. 1,000만원 자산은 10,000,000원 잔액으로 유지하며 12로 나누지 않는다. 연 상여 12,000,000원은 별도 연평균 환산에서만 월 1,000,000원으로 계산한다.
3. 정기 합산소득 6,000,000원, 비주거 고정비 600,000원, 변동비 1,800,000원에 가정계수 0.85, 주거 운영비 1,000,000원, 기존 상환 500,000원, 신규 상환 300,000원이면 잉여자금은 2,070,000원이다. 예시 금액이며 금융 권고가 아니다.
4. 상여가 월 평균 소득에 이미 포함됐으면 두 번 더하지 않는다. 이미 합가한 실제 지출에는 다시 0.85를 적용하지 않는다.
5. 주거비에는 대출 상환이 없고, 대출 상환은 정확히 한 번 차감한다. 시나리오에서 상환 완료된 기존 대출을 유지 비용으로 다시 차감하지 않는다.
6. 모든 가치관 답이 같으면 차이 카드0개, 공통 기준 카드만 생성한다. 동률이면 매 요청·새로고침에서 같은 순서다.
7. skipped, unknown, withheld는 0이나 3점이 아니다. 불충분한 영역은 partial/unavailable이며 보고서 전체 장애를 유발하지 않는다.
8. 소득0·자산0·음수 잉여자금·지난 목표일·금리0·남은기간0·보증금 반환 전 사용 불가를 각각 검사한다. 0개월의 상환 추정은 입력 오류로 처리한다.
9. 로그인된 A라도 B 입력 직접 조회는 불가하다. A만 제출한 상태의 상태/결과/계획/에러/로그 어디에도 B의 비공개 정보가 없어야 한다.
10. 두 최종 제출의 경쟁과 두 결과 요청의 경쟁에서 같은 입력·계획 버전에 대한 단일 공개 결과만 확정한다. stale revision은409다.
11. 금액 공개 거부는 합산금액과 파생 대화에서도 반영된다. 철회 후 이미 생성된 reportId로 조회해도 거부된다.
12. 정책 데이터·LLM이 없어도 템플릿 결과는 열린다. 정책 unavailable을 자격 없음으로 표시하지 않는다.
13. 합의 version 변경 시 이전 확인은 모두 무효다. 양측 확인 없이는 agreed가 아니다.
14. 만료 후 TTL 삭제 전에도 조회가 차단된다. 브라우저 저장소·공유카드·일반 분석 이벤트에 민감 데이터가 없다.
15. 기존 Light 전체 테스트와 OpenAPI 생성·타입검사를 통과시킨다. 이번 문서 작성에서는 앱 테스트를 실행하지 않았다.

## 11. 승인할 사항과 다음 단계

제품 방향은 사용자 요청과 새 정체성 문서에 따라 공동 대화 중심으로 제안한다. 아래는 자료에 없는 신규 제안이므로 확정 사항과 구분한다.

- 첫 출시에서 숫자형 Say-Do와 LLM·정책 매칭을 제외하고 중립 템플릿 대화로 제공하는 범위.
- 고정 16개 유형 조합 대신 답변 근거가 분명한 서술형 태그부터 제공하는 범위.
- 공개 동의·동일 공동 계획 version까지 포함한 공동 공개 조건.
- 중요 주제 선택과 동률 규칙, 30건 부채 상한.
- 초안30일/결과90일 보관기간.

로그인 제공자는 카카오로 사용자 확인이 끝났다. 카카오 앱 등록 상태, 요청할 최소 정보, 콜백 주소와 환경 변수 구성은 구현 준비 단계에서 확인한다. 계정 식별을 위한 로그인과 재무정보의 파트너 공개 동의는 별개로 유지한다.

검토 후 정체성·계산 규칙을 확정 명세로 정리하고, 로그인/딥 입력·계산/공동 결과·합의로 실행 계획을 분리한다. 현재 문서는 코딩 착수나 자동 배포의 승인이 아니다.

### 구현 계획 연결

후속 사용자 요청에 따라 계산·템플릿 중심 첫 출시의 [통합 구현 계획](../plans/2026-09-03-deep-mvp-implementation.md)을 작성했다. 카카오 인증, 입력·계산, 공동 공개·출시 검증의 세 계획으로 나누었다. 계획 작성은 요청받았지만 코딩과 프로덕션 변경은 아직 수행하지 않았다. 보관기간 등 위에 표시한 제안값은 실행·출시 전 확인 대상이다.
