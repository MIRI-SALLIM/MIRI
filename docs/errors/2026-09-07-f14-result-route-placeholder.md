# F14 제출 완료 뒤 결과 목적지가 준비 중으로 남아 있던 문제

- 작성일: 2026-09-07
- 관련: 이슈 #103, PR 미정, 커밋 미정

## 무엇이 잘못됐나

딥 상태가 `ready`가 되어도 대기 화면의 다음 링크가 공동 계획으로 돌아갔고,
`/deep/result/:sessionId`는 준비 중 플레이스홀더를 렌더링했다. 제출 API가 성공해도
사용자가 공동 리포트에 도달할 수 없는 상태로, 라우트 회귀 테스트와 F14 수직 흐름 점검에서
발견했다. 같은 경로 점검에서 계획 화면이 입력·질문·제출로 이어지지 않았고, 이미 한쪽이
제출해 계획이 잠긴 경우 다른 쪽의 계획 확인 버튼도 사라지는 문제를 추가로 발견했다.

## 원인

- **설계적 원인**: F14(제출·대기)와 F15(리포트)를 분리해 구현할 경우 제출 성공 뒤의
  목적지를 함께 검증하지 않는 구조였다. 계획 문서가 두 단계를 함께 병합하도록 요구했지만
  기존 화면은 F14 이전 단계의 상태 허브만 갖고 있었다.
- **코드적 원인**: `DeepWaitingPage`의 `ready` 분기가 계획 링크를 재사용했고,
  `AppRoutes`의 결과 라우트가 `DeepPlaceholderPage`를 가리켰다. `DeepPlanPage`에는
  확인 후 입력으로 이어지는 링크가 없었고, 잠긴 계획 분기에서 서버가 허용하는 현재
  버전 확인 버튼을 숨겼다. 제출 전 요약은 `values.<id>: null`을 응답으로 잘못 보기도 했고,
  계획 버전 경합 오류가 제출 화면에 머물렀다.

## 해결

`GET /result`의 `waiting|ready` 판별 유니온을 런타임 파서로 연결하고, 결과 페이지에서
5개 계산 블록·공유 동의 안내·알려진 이슈 질문·한계 안내를 렌더한다. `ready` 상태는
결과 링크로 이동하고, 랜딩의 딥 CTA는 `/deep` 진입 화면으로 열되 이후 직접 노출되는
경로에는 미완성 목적지를 남기지 않았다. 계획 확인 후 입력 링크와 제출 완료 대기자의
결과 준비 상태 링크를 추가하고, 잠긴 계획에서도 확인할 수 있게 했다. 제출 요약은
`null`을 미응답으로 취급하며, 계획 버전 경합은 최신 계획 화면으로 되돌린다.

## 재발 방지

`AppRoutes.test.tsx`의 `routeCases`에 제출·결과 라우트를 추가하고, 대기 화면의 `ready`
링크 및 결과 상태/블록 테스트를 함께 둔다. 계획→입력 링크, 잠긴 계획 확인,
`null` 미응답 요약, 계획 버전 경합 복귀도 회귀 테스트로 고정했다. 다음 단계에서도 새 CTA를 열기 전에
클릭 이후 목적지의 라우트가 플레이스홀더인지 먼저 확인한다.
