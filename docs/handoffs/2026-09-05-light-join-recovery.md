# Light 초대 참여 응답 유실 복구 — 이슈 #51

2026-09-05. #51 수정 범위 기록이다. 커밋·푸시는 Git 이력으로 확인하며 운영 배포·이슈 종료와는 구분한다.
딥모드 UX 계획의 구현은 계속 보류한다.

## 원인과 수정

- Light `POST /api/v1/invitations/{code}/join`은 Idempotency-Key를 받지만 저장소에 전달하지 않았고,
  이미 참여자가 있으면 복구 여부를 확인하기 전에 409를 반환했다.
- 이제 같은 세션·같은 요청 키·같은 닉네임이면 동일 invitee 토큰/쿠키를 재발급한다.
  참가자 추가는 Mongo의 기존 조건부 갱신을 사용하고 재요청은 기존 참여자만 읽는다.
  답변·제출 상태·만료 시각을 초기화하거나 토큰을 매번 회전하지 않는다.
- 토큰은 서버 pepper와 세션 ID·요청 키를 도메인 구분 HMAC으로 연결해서 재현한다.
  DB에는 기존 `tokenHash`만 저장하며 원문 토큰과 join 키는 저장하지 않는다. 추가 컬렉션·인덱스·마이그레이션은 없다.
- 다른 키/다른 닉네임/키 없는 중복 참여는 기존 409, 만료·삭제된 초대는 기존 404다.
  공개 초대 미리보기는 참여 완료 후 계속 중립적인 404를 반환한다.
- 프론트의 세션 생성/초대 참여 버튼은 같은 실패 작업을 재클릭할 때 같은 UUID를 재사용하고 성공 후 버린다.
  초대 코드가 바뀌면 새 키를 만든다. 자동 POST 재시도는 추가하지 않는다.
- 재연결·포커스 재조회가 점유된 초대의 404를 가져와도 이미 확인한 초대 화면을 유지한다.
  재시도 버튼의 키가 사라지는 것을 막으며, 실제 참여 가능 여부는 POST에서 서버가 판단한다.

## 적용 경계

- 키는 버튼의 메모리에만 존재한다. 실패 뒤 같은 화면에서 다시 누르는 복구가 대상이다.
  탭 종료·전체 새로고침·화면 이탈로 키가 사라진 뒤의 자동 복구까지 지원한다고 안내하지 않는다.
  원문 키는 복구 자격 정보처럼 취급해 URL·웹 저장소·로그·분석 이벤트에 넣지 않는다.
- 배포 전에 키 없이 이미 참여한 세션의 응답이 유실된 경우는 소급 복구할 수 없다.
- `POST /sessions` 백엔드는 이미 키를 처리하므로 이번에 바꾸지 않았다.
  기존 세션 생성의 동시 요청/토큰 회전 설계까지 재작성하지 않는다.
- Deep v3와 카카오 OAuth는 별도 경로이며 이번 수정 대상이 아니다. JSON/OpenAPI 구조는 변경하지 않는다.
- 원격 develop에는 별도 프론트 후속 변경이 있으므로, 통합 시 해당 변경을 보존하고 CI를 다시 확인한다.

## 확인 방법

- 실제 TestClient에서 첫 join 쿠키 유실 → 같은 키 재요청 → 동일 쿠키로 내 세션/입력 조회.
- 다른 키/본문 거절, 만료/삭제 차단, 세션별 토큰 분리, 입력·제출 상태 보존.
- 메모리 및 Mongo 경계 대역에서 같은 키/다른 키 경쟁과 저장소 재생성 후 재요청.
- 실Mongo 동시 같은 키 4건 테스트도 `test_mongo_concurrency.py`에 추가했다.
  로컬 검증은 Atlas를 사용하지 않으며, 실Mongo 검증은 별도 DB를 제공하는 CI 실행이 필요하다.
- 프론트는 실제 API 클라이언트+버튼/초대 페이지를 사용해 실패 후 키 재사용, 새 작업의 키 분리,
  초대 백그라운드 404 이후 수동 복구, 자동 POST 재시도 없음, 웹 저장소 키 미보관을 검사한다.
