# 딥 세션 재개·종료 계약의 UI 오해

- 작성일: 2026-09-06
- 관련: 이슈 #88, PR #90

## 무엇이 잘못됐나

딥 세션 F10 라운드 2 리뷰에서 새로고침·허브 재개 시 초대 코드가 사라지고, 참여자 B에게도 초대 카드가 보이며, 401/404 상태에서 자동 재확인 안내만 남는 문제가 발견됐다. 브라우저 저장소가 차단되면 서버에서 성공한 세션 생성이 클라이언트 mutation 실패로 바뀌고 재시도 시 중복 세션 위험도 있었다.

## 원인

- **설계적 원인**: v3 API에 세션 초대 코드 재조회 계약이 없는데도 대기 화면이 항상 초대 코드가 있다고 가정했다. 또 허브 재개 query key와 실제 query 등록이 연결되지 않아 무효화가 동작하지 않았다.
- **코드적 원인**: 대기 화면이 `SessionV3.role`을 전달받지 않았고, polling 오류 종류를 화면에 노출하지 않았으며, `saveActiveDeepSessionId`가 `sessionStorage.setItem` 예외를 그대로 전파했다. 종료 확인 문구와 만료 오류 분기도 백엔드의 공동 종료 동작과 맞지 않았다.

## 해결

초대 코드는 capability이므로 공개 세션 UUID만 저장한다는 보안 규칙을 우선해 저장하지 않기로 결정했다. 생성·참여 직후 URL에 역할을 함께 남기고, 코드가 없는 재개 화면은 링크를 다시 만들 수 없음을 설명하며 세션 종료·새 세션 시작 경로를 제공한다; B 역할에는 초대 UI를 숨긴다. 401/404는 로그인 또는 딥모드 첫 화면 CTA로 분기하고, 복구 가능한 오류는 수동 재확인 버튼을 제공한다. 저장소 쓰기는 best-effort로 감싸고, 사용되지 않는 query key/export와 무의미한 invalidation을 제거했으며, 종료 확인 문구는 상대 참가자와 입력·결과까지 함께 닫힌다는 사실을 명시했다.

## 재발 방지

역할별 대기 화면, 초대 코드 부재, 401/404/네트워크 오류, 저장소 차단, 공동 종료 문구에 회귀 테스트를 추가했다. API snapshot check, lint, typecheck, 전체 Vitest, production build를 완료 전 실행하고, v3에 초대 코드 재조회 API가 추가되기 전에는 capability를 브라우저 저장소에 보관하지 않는다.
