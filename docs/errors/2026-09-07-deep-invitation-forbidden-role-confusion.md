# 딥 초대 조회 403을 로그인 만료로 해석한 문제

- 작성일: 2026-09-07
- 관련: 이슈 #117, PR/커밋 없음 (코디네이터가 통합)

## 무엇이 잘못됐나

딥 초대코드 조회의 403 응답에 `PARTICIPANT_UNAUTHORIZED` 코드가 붙으면 공통 오류 분류가 `unauthorized`가 되어, 정상적으로 참여한 사용자가 로그인 만료 화면을 볼 수 있었다. 초대코드를 URL에만 두던 화면은 새로고침 뒤 코드를 잃고, 역할을 403으로 추론하면 이 두 문제가 한 화면에서 엇갈렸다.

## 원인

- **설계적 원인**: 초대 조회의 생성자 전용 권한 응답을 역할 신호로 사용하려 했고, capability인 초대코드를 URL에 유지했다.
- **코드적 원인**: `shared/api/errors.ts`가 본문 코드로 `kind`를 덮어썼고, 딥 대기 화면과 상태 훅이 오류 종류를 상태 코드보다 먼저 신뢰했다.

## 해결

403은 `error.status`를 먼저 확인해 참여자 상태로만 안내하고, 역할은 세션 생성·참여 직후 `sessionStorage`에 저장했다. 생성자만 상태 조회가 성공한 뒤 불변 초대 API를 호출하며, 역할 미상 사용자는 명시적으로 버튼을 눌렀을 때만 조회한다. URL에는 세션 ID만 남기고, 서버에서 받은 코드로 화면의 초대 링크를 조립한다.

## 재발 방지

403 오류 매핑·재시도 금지, 상태 훅의 HTTP 상태 우선 판별, 역할 저장소와 초대 API 요청 게이트, 생성자·참여자·역할 미상 화면 테스트를 반영했다. 이후 권한 오류를 분기할 때는 본문 코드나 `kind`보다 HTTP 상태와 계약상 호출 주체를 먼저 확인한다.
