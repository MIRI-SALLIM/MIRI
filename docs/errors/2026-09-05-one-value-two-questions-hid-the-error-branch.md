# 판정 값 하나를 두 질문에 써서 오류 화면이 가려졌다

- 작성일: 2026-09-05
- 관련: 이슈 #44, #54, PR #55, #56, 커밋 `efcf06a`, `5bc4e56`
- 관련 없는 두 사건이 같은 원인을 공유한다

## 무엇이 잘못됐나

`LightFormPage`에서 조회가 실패했는데 **오류 문구 대신 "질문을 불러오는 중..."이 영구히 남는** 문제가 두 번, 서로 다른 형태로 나타났다.

**사건 1 — 이슈 #44 리팩터링이 만든 회귀.** hydration 판정을 상태 유니온으로 정리하면서 `getLightFormHydrationState`가 반환하는 상태를 렌더 게이트에 그대로 재사용했다. 그 함수는 `inputQuery.data === undefined`이면 fetch가 **오류로 확정된 뒤에도** `pending-input`을 반환한다. 렌더 분기가 로딩을 오류보다 먼저 검사하므로 오류 문구에 도달하지 못한다. `codex-sol-high` 검증이 병합 전에 잡았다.

**사건 2 — 그 이전부터 있던 결함(이슈 #54).** 같은 렌더 분기의 `!isHydrated`가 같은 일을 한다. `isHydrated`는 `hydrate`가 호출될 때만 `true`가 되고 `hydrate`는 데이터가 있어야 호출되므로, 조회가 실패하면 영구히 `false`다.

**오류 분기 전체가 도달 불가능이었는데 아무도 몰랐다.** `pageErrorMessage`를 단정하는 테스트가 하나도 없었기 때문이다.

## 원인

**설계적 원인**: 하나의 값이 **두 개의 다른 질문**에 답하도록 쓰였다.

| 값 | 원래 뜻 | 잘못 쓰인 곳 |
| --- | --- | --- |
| `hydrationState` | effect가 스토어에 써야 하는가 | 렌더가 아직 기다리는가 |
| `isHydrated` | 스토어가 채워졌는가 | 렌더가 아직 기다리는가 |

두 질문의 답은 **정확히 fetch가 아무것도 없이 끝났을 때 갈린다.** effect 입장에서는 쓸 데이터가 없으니 쓰지 않는 것이 맞고, 렌더 입장에서는 기다림이 끝났으니 결과(오류)를 보여줘야 한다.

값이 하나뿐일 때는 그 분기점이 보이지 않는다. 이름이 `pending-input`이면 "아직 오지 않았다"로 읽히고, 실제로는 "왔는데 없다"도 포함한다는 것이 드러나지 않는다.

**코드적 원인**: `LightFormPage.tsx`의 렌더 분기가 로딩 조건을 오류 조건보다 먼저 평가한다. 두 조건이 동시에 참일 수 있는데 순서가 그것을 결정한다.

## 해결

**상태에 확정 실패를 추가했다**(#44 라운드 3).

```ts
type LightFormHydrationState = "failed-data" | "pending-input" | "pending-status" | "ready";

if (sessionId === null || !inputFetched) return "pending-input";
if (!statusReady && !isReadOnly) return "pending-status";
if (!hasInput || questionCount === 0) return "failed-data";   // 확정 실패
return "ready";
```

렌더 게이트는 pending 두 상태만 로딩으로 취급한다. effect는 `ready`에서만 도므로 영향이 없다.

**오류 분기를 로딩보다 먼저 평가했다**(#54). 판단 근거는 이 화면이 렌더를 막고 기다리는 조회가 전부 `retry: false`라 **오류가 최종**이라는 것이다 — 다른 조회가 진행 중이어도 폼으로 바뀔 수 없으므로 기다리는 것은 메시지를 늦출 뿐이다.

`!isHydrated`는 로딩 조건에 남겼다. **그것은 실제 상태를 방어한다** — 모든 조회가 성공했지만 hydration effect가 아직 돌지 않은 구간이다. React Profiler로 실측하니 세 조회 동시 resolve 시 2 commit, 순차 resolve 시 4 commit이었다.

## 재발 방지

**두 사건 모두 테스트가 없어서 통과했다.** 각각 회귀 테스트를 넣었다.

- #44: `isHydrated: true` 상태에서 `/me/input` 503과 빈 질문 배열 — 2개
- #54: `isHydrated`를 시드하지 **않고** 질문·입력·active-session 실패 — 3개

**red를 매번 확인했다.** 수정을 되돌린 상태에서 정확히 그 테스트들만 실패하는 것을 보고 복구했다.

**앞으로 의심할 것**: 파생 값을 **두 곳 이상에서 소비**할 때, 각 소비처가 그 값에 묻는 질문이 같은지 확인한다. 다르면 값을 나눈다. "리팩터링이라 동작이 같다"는 주장은 **소비처마다** 검증해야 하고, 특히 렌더 분기의 **순서**는 조건이 동시에 참일 때만 드러나므로 전수 조합 대조가 필요하다.

그리고 **오류 문구를 단정하는 테스트가 없으면 그 분기는 도달 불가능일 수 있다.** 화면의 오류 경로에 테스트가 있는지 먼저 본다.
