# 커밋 메시지에 확인하지 않은 일반화를 다섯 번 썼다

- 작성일: 2026-09-05
- 관련: 이슈 #42, #44, #47, #53, #57 / PR #52, #55, #58, #60, #61
- 개별로는 사소하지만 **다섯 번 반복된 패턴**이라 기록한다

## 무엇이 잘못됐나

`codex-sol-high` 검증이 커밋 메시지의 사실 오류를 다섯 번 잡았다. 전부 코디네이터가 쓴 것이고, 전부 같은 형태다.

| # | 내가 쓴 것 | 실제 |
| --- | --- | --- |
| 1 | "`main.py:825`가 `repository.join()` 호출" | `:825`는 `question_count` 계산. 호출은 `:826` |
| 2 | "`POST /sessions`도 `Idempotency-Key`를 쓰지 않는다" | `main.py:698`이 넘기고 `session_repository.py:103-116`이 재생한다. 안 쓰는 것은 `join`뿐 |
| 3 | "`completedAt: None`이 전부 filter clause" | `:140`과 `:241`은 참여자 생성 초기값 |
| 4 | "#46과 #47 둘 다 테스트가 없었다" | #46 수정 커밋 `de69218`에는 테스트가 있었다 |
| 5 | "두 페이지 다 `e2e/accessibility.spec.ts` 경로 밖" | waiting 페이지는 방문한다. axe가 로딩 종료 후 실행돼 못 잡은 것 |

추가로 이슈 본문과 브리프에도 같은 형태가 있었다.

- "hydration 직전 **한 프레임**" — 실측하니 동시 resolve 2회, 순차 resolve 4회
- "테두리 **양쪽 모두** 3:1을 넘어야 한다" — WCAG 이해 문서는 바깥 배경을 기준으로 본다
- "native input **4개**" — `<input>` 3개와 `<select>` 1개

## 원인

**코드를 읽는 단계가 아니라 읽은 것을 산문으로 옮기는 단계에서 발생했다.** 다섯 건 다 코드는 정확히 읽었고, 그것을 문장으로 만들면서 확인하지 않은 범위를 붙였다.

공통 형태가 셋이다.

- **한정어를 붙였다** — "전부", "둘 다", "유일한", "모든". 실제로 전수 확인한 것은 일부였다
- **행 번호를 기억으로 썼다** — 근처를 봤지만 그 줄을 다시 열지 않았다
- **인접한 사실로 확장했다** — "#46이 안 잡혔다"에서 "경로 밖이다"로. 안 잡힌 것은 맞고 이유가 달랐다

리뷰가 매번 **원본을 다시 열어** 잡았다. 즉 확인 가능한 것이었고 내가 확인하지 않은 것이다.

## 해결

건별로 정정했고, 워크트리 브리프의 "사실이 아닌 것을 쓰지 마라" 절에 실제 사례로 누적했다. 에이전트들도 같은 실수를 하므로 그 목록이 공유된다.

정정 자체는 문장 교체였지만, **네 번째와 다섯 번째는 앞의 셋을 겪은 뒤에도 발생했다.** 사례를 나열하는 것만으로는 막히지 않는다.

## 재발 방지

**행 번호를 쓸 때 그 줄을 다시 연다.** `sed -n '<line>p'` 한 줄이면 된다.

**한정어를 쓸 때 자문한다** — "전부"라고 쓰려면 전수 조회를 했는가. 안 했으면 범위를 좁혀 쓴다. "확인한 범위에서는"이 정확하면 그렇게 쓴다.

**인과를 쓸 때 원인을 분리해 확인한다.** "A가 B를 못 잡았다"와 "A가 B를 방문하지 않는다"는 다른 주장이고, 후자가 참이 아니어도 전자는 참일 수 있다.

**앞으로 의심할 것**: 커밋 메시지의 사실 주장은 코드 주석보다 검증이 느슨해지기 쉽다 — 컴파일러도 테스트도 보지 않기 때문이다. 그러나 그것은 다음 사람이 **왜 이렇게 했는지**를 알아내는 유일한 기록이고, 거기 적힌 거짓은 그 사람의 판단을 틀리게 만든다. 리뷰가 커밋 메시지를 검증 대상에 포함해야 하는 이유다.
