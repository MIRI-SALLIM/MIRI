## 1. 정체성: 사람을 판정하지 않고, 계획의 빈칸을 드러낸다

> 우리는 행복을 만들어주지 않는다. 꺼내기 어려웠던 대화를 꺼내기 쉽게 해줄 뿐이다.

딥모드의 완성은 긴 설문이나 좋은 궁합 결과가 아니다. **두 사람이 얼마를, 언제, 어떤 조건으로 부담할지 말할 수 있게 되는 것**이다. 결혼 여부와 무관하게 함께 살 돈의 기준을 만드는 서비스다. 라이트의 상대 예측 게임·유형 놀이를 필수 선행 과정으로 만들지 않는다.

최근 사용자 방향을 반영해 원문의 “방어적으로 만들면 정확한 문장도 폐기”는 다음처럼 조정한다. **비난은 제거하되, 의사결정에 필요한 불편한 사실은 제거하지 않는다.** 부족액·미정인 책임·서로 수락하지 않은 조건을 분명하게 쓰고 바로 다음 결정 질문을 붙인다.

| 쓰는 문장 | 쓰지 않는 문장 |
|---|---|
| “입력한 재원으로는 잔금일까지 2,300만 원이 부족합니다.” | “두 분은 아직 함께 살 준비가 안 됐습니다.” |
| “각자 제시한 월 분담액을 합쳐도 공동예산보다 40만 원 적습니다.” | “두 분 모두 책임을 피하고 있습니다.” |
| “이 분담안은 아직 두 사람 모두의 확인을 받지 못했습니다.” | “통장 관리 취향이 다르니 돈 문제로 싸울 가능성이 높습니다.” |
| “공유된 정보로는 월 여유자금을 계산할 수 없습니다.” | “상대가 무언가 숨기고 있습니다.” |

표준 결과 문장 구조는 **관찰된 답·숫자 → 이 계획에서의 의미 → 지금 결정할 질문 → 제안/확인/보류**다. “조금 더 이야기해 보세요”만으로 끝내지 않는다.

## 2. 채택할 방식과 전체 흐름

세 가지 접근을 비교했다. 긴 고정 설문은 단순하지만 불필요한 질문이 많고, 자유 AI 상담은 표현이 유연하지만 필수 숫자와 동의 여부가 누락되기 쉽다. **구조화된 기본 질문 + 조건부 추가 질문 + 규칙 기반 결과·대화**를 채택하는 안이다. AI 유무와 관계없이 끝까지 사용할 수 있어야 한다.

```text
로그인·둘의 공간 만들기
  → ① 함께 계산할 계획 정하기
  → ② 각자의 돈 현황 입력
  → ③ 실제로 투입할 수 있는 돈 확인
  → ④ 가치관 10문항 + 내 분담안·수용 조건
  → ⑤ 공개 범위 확인·양쪽 제출
  → ⑥ 부족액 / 미확정 / 의견 차이 / 미합의 분리
  → ⑦ 필요한 질문부터 함께 답하고 대안 비교
  → ⑧ 우리 기준표: 확인한 것·남은 것·다시 볼 날짜
```

각자 작성은 자동저장·중단 후 재개를 지원하는 방향이다. “15분”은 UX 목표이지 확정 소요시간이 아니다. 자산·부채 개수에 따라 늘어나는 입력과 둘이 대화하는 시간은 별도다. 결과를 보려면 숫자를 전부 공개해야 한다는 압박을 주지 않는다.

질문 추가 기준은 세 가지다. 답이 **계산을 바꾸거나, 필요한 다음 질문을 바꾸거나, 구체적인 공동 결정을 남겨야 한다.** 어느 것도 하지 않는 질문은 넣지 않는다.

조건부 질문 운영 규칙:

- 개인 작성 중에는 본인 입력과 명시적으로 공유된 계획만 분기 조건에 쓴다. 상대 입력을 읽어 질문 수나 순서를 바꾸지 않는다.
- “부채 없음”이면 대출 상세는 건너뛰고, “부채 모름/비공개”이면 부채 0원으로 계산하지 않는다. 계산에 필요한 질문도 모름·비공개를 허용한다.
- 앞선 답을 수정하면 종속 답의 유효성을 다시 검사한다. 자산 종류·사용 여부를 바꾼 뒤 남은 예전 답을 몰래 계산하지 않으며, 삭제/비활성화할 내용을 본인에게 알린다.
- 진행률은 현재 적용되는 질문을 기준으로 한다. 추가 자산·부채로 질문이 늘면 그 이유를 표시하고 고정 문항 수를 약속하지 않는다.
- 공개 후 공동 질문은 고정된 리포트 버전의 근거로 생성한다. 새로고침만으로 새로운 질문·숫자·미합의 상태를 만들어내지 않는다.

## 3. ① 함께 계산할 계획: 무엇을 기준으로 답하는가

이 화면만 처음부터 공동 문서다. 한 사람이 초안을 작성하고 둘이 같은 버전을 확인한다. 이 확인은 “이 조건으로 계산하자”는 뜻이지, 돈을 낼 의무나 모든 생활 규칙에 동의했다는 뜻이 아니다.

| ID | 실제 질문 문구 | 답 / 용도 |
|---|---|---|
| P1 | “지금 두 분은 함께 살고 있나요?” | 각자 예/아니요/상황 설명 보류. 응답 불일치 시 현재 합산 구조 확인이 필요하며 임의 추정하지 않음 |
| P2 | “언제부터의 생활을 계산할까요?” | 시작월. 이미 함께 살면 예산 적용 시작월 |
| P3 | “집은 어떻게 할 계획인가요?” | 현재 집 유지 / 월세 / 전세 / 매매 / 아직 미정 |
| P4 | “집을 마련하는 데 필요한 보증금 또는 매매대금은 얼마인가요?” | 일회성 총액. 새 대출을 미리 뺀 자기자본 금액과 혼용하지 않음 |
| P5 | “그 돈은 언제까지 준비해야 하나요?” | 납부일·금액. 초기에는 잔금 1건, 계약금 등 앞선 지급이 있으면 추가 |
| P6 | “이사·중개·가전 등 한 번만 드는 비용은 얼마로 잡을까요?” | 항목별 또는 중복 없는 합계·필요일. 주거비와 분리 |
| P7 | “함께 산 뒤 월세·관리비·공과금은 월 얼마로 예상하나요?” | 월 주거 운영비. 대출 상환 제외 |
| P8 | “매달 공동으로 낼 비용은 어디까지인가요?” | 주거비·식비·공동 구독·기타의 범위와 항목별 목표액. 개인비와 중복 금지 |
| P9 | “주거비 외에 함께 모을 목표가 있나요?” | 선택 1개: 이름·목표액·목표월. 없음을 허용 |

P4~P6은 집 유지 시 숨기되, 새로 필요한 일회성 비용이 있는지 한 번 확인한다. P3 미정이면 현재 기준 월 현황과 대화는 제공하되 새 주거 초기자금 계산은 미완성으로 둔다. P8 미정이면 분담 공백 금액을 계산하지 않고 “공동비 범위부터 정해야 합니다”를 표시한다.

현재 구현에 없는 납부 일정·공동비 범위 등은 신규 필드다. 기존 `startMonth`만으로 정확한 잔금일을 안다고 표시하지 않는다.

## 4. ② 각자의 돈 현황: 자산·대출을 빠뜨리지 않는 질문

모든 개인 질문은 상대 답과 무관하게 나온다. 입력 전 안내는 다음과 같다.

> “상대에게 맞춰 답하지 않아도 됩니다. 지금 아는 사실과 본인이 원하는 기준을 적어주세요. 모르는 금액과 0원은 다르게 처리합니다. 제출 전 공유 범위를 확인할 수 있습니다.”

금액은 `정확히 앎 / 대략 앎 / 모름 / 이번에는 공개하지 않음`으로 구분한다. 아는 0원은 유효하며 추정은 별도 표시한다. 자산·부채가 없다는 답은 명시적으로 받는다. 미응답을 “없음”으로 채우지 않는다.

### 4.1 소득과 지출

| ID | 실제 질문 문구 | 분기 / 결과 연결 |
|---|---|---|
| F1 | “세금 등을 뺀 뒤 한 달에 실제로 들어오는 돈은 얼마인가요?” | 금액·기준월. 일정하지 않으면 사용자가 선택한 기간의 평균과 기간을 함께 기록; 안정적 소득으로 단정하지 않음 |
| F2 | “이 금액에 상여·성과급도 나눠 넣었나요?” | 포함/미포함/모름. 별도 상여의 중복 반영 방지 |
| F3 | “별도로 받는 상여가 있다면 세후 얼마이고, 언제 들어오나요?” | 있을 때만. 금액·예정월·확정 여부. 연평균 참고와 실제 입금 시점 분리 |
| F4 | “매달 고정으로 나가는 돈은 얼마인가요? 집과 대출은 다음에서 따로 적습니다.” | 통신·보험·구독·가족 지원·기타. 본인의 실제 부담분 |
| F5 | “식비·교통·쇼핑·여가에는 한 달에 얼마나 쓰나요?” | 카테고리별 금액. 이미 함께 살면 공동 총액을 양쪽이 각각 전액 입력하지 않도록 확인 |
| F6 | “지금 집에 매달 내는 월세·관리비·공과금은 얼마인가요?” | 본인 부담액. 보증금·대출 원리금·저축 이체 제외 |

카드 결제액에 대출·주거비를 이미 포함했다면 중복 안내를 한다. 단위 오류는 재확인을 요청하되 소득이 적거나 지출이 많다는 이유로 입력을 막지 않는다. 실제 0원 지출도 허용한다. 남는 돈은 “계산상 여유자금”이지 실제 저축 실적이 아니다.

### 4.2 부채: 월 상환액부터, 필요한 경우 상세 입력

| ID | 실제 질문 문구 | 분기 / 결과 연결 |
|---|---|---|
| L1 | “현재 갚아야 할 돈이 있나요? 전세대출·학자금·가족에게 빌린 돈도 포함해 주세요.” | 없음/있음/모름/비공개. 종류·잔액을 반복 입력 |
| L2 | “이 돈 때문에 매달 얼마가 나가나요?” | 아는 상환액 우선. 이자만 내는지 원금도 갚는지 구별 |
| L3 | “상환액을 계산하려면 금리·남은 기간·상환 방식을 확인할 수 있나요?” | L2 모름 또는 미래 상환 일정 계산을 원하는 경우만. 종류로 계약 조건 추측 금지 |
| L4 | “함께 살기 시작해도 이 대출을 계속 갚나요, 그 전에 정리하나요?” | 유지/전액 정리/일부 정리/아직 미정 + 정리일·금액 |
| L5 | “정리할 돈은 어디에서 나오나요?” | 보증금 반환금 등 기존 자금 항목 연결 / 다른 재원 / 미정 |
| L6 | “일부만 갚은 뒤에는 매달 얼마를 내게 되나요?” | 일부 정리 시만. 모르거나 계약 정보가 부족하면 변경 후 월 흐름은 미확정 |

가족에게 받는 돈도 돌려줄 의무가 있으면 부채다. 제3자의 이름·계좌·계약서·주민번호는 요구하지 않는다. 신규 주거대출은 실제 사용자 입력 조건으로만 계산하며 한도·승인을 추정하지 않는다.

### 4.3 자산: 전체 규모와 쓸 돈을 분리

| ID | 실제 질문 문구 | 분기 / 결과 연결 |
|---|---|---|
| A1 | “예금·적금·현금처럼 모아둔 돈은 얼마인가요?” | 반복 항목 또는 중복 없는 합계 |
| A2 | “현재 집에 묶여 있는 전세·월세 보증금이 있나요?” | 보증금 총액과 본인 지분. 연결 대출을 빼기 전 금액 |
| A3 | “주식·펀드 등 투자자산은 얼마인가요?” | 현재 평가액·기준일. 현금과 동일 취급 금지 |
| A4 | “청약통장·부동산·그 밖의 자산이 있나요?” | 유형별 본인 보유분. 정책 자격 판단을 위해 가입기간 등을 추가 수집하지 않음 |
| A5 | “이 금액은 본인 몫인가요, 두 분이 함께 가진 돈인가요?” | 각자 본인 지분 금액만 자산 합계에 반영. 공동 항목 중복은 식별·재확인 |

자산별 본인 잔액은 부채 차감 전 금액으로 통일하고 순자산은 별도 계산한다. 부모 지원이 포함됐는지 모르는 자산을 “자력으로 모은 돈”으로 해석하지 않는다.

## 5. ③ 실제 쓸 수 있는 돈: 이번 확장의 핵심

모든 자산을 공동생활에 내라고 묻지 않는다. 먼저 “이 자산 중 이번 계획에 사용할 돈이 있나요?”를 묻고, **사용하려는 항목에만** 아래 질문을 연다. 사용하지 않는 자산은 자산 현황에만 남긴다.

| ID | 조건 | 실제 질문 문구 | 답이 바꾸는 것 |
|---|---|---|---|
| U1 | 모든 투입 자산 | “이번 계획에 사용할 돈은 얼마인가요?” | 보유액과 투입 의사 분리. 주거용·목표용·남겨둘 돈 중복 배정 방지 |
| U2 | 모든 투입 자산 | “이 돈을 실제로 쓸 수 있는 날짜는 언제인가요?” | 이미 사용 가능 / 날짜 입력 / 미정. 납부일에 늦는 재원 구별 |
| U3 | 보증금 | “돌려받을 본인 몫의 보증금은 얼마인가요?” | 명목 보증금과 예상 반환액 구별. 공제액이 불명확하면 추정 표시 |
| U4 | 보증금 | “반환받을 때 먼저 갚아야 하는 대출이 있나요?” | 기존 대출 ID 연결·상환액·상환일. 없음을 명시 가능 |
| U5 | 보증금 | “반환 날짜와 금액을 확인했나요, 아직 예상인가요?” | 입력상 확인된 예정 재원 / 예상 재원 / 미정 구별. 은행 검증 완료라는 뜻 아님 |
| U6 | 투자·청약·부동산 | “이번 계획을 위해 매도·해지할 예정인가요? 비용을 빼고 얼마를 언제 쓸 수 있나요?” | 평가액을 즉시 사용 가능한 현금으로 넣지 않음. 실제 처리되지 않으면 예정/추정 |
| U7 | 보유자산 외 지원·새 대출 | “추가로 받을 예정인 돈이 있나요? 금액과 날짜는 확인됐나요?” | 기존 자산에 이미 들어온 돈이면 새 재원으로 중복 등록 금지 |
| U8 | 지원금 있음 | “돌려줘야 하는 돈인가요?” | 지원/차입 구분. 반환 의무 있음이면 부채 연결, 없으면 상환 부담 추가하지 않음 |
| U9 | 필요한 시점에 부족 | “부족한 돈을 마련할 방법이 정해졌나요?” | 자기 입력 점검 단계에서는 본인 데이터만 사용. 공동 부족액 질문은 공개 이후에만 생성 |

### 5.1 자금표 계산의 불변 조건

- 자산 규모, 순자산, 사용 가능한 순재원, 실제 투입 예정액은 서로 다른 수치다.
- 보증금 반환 순재원 = 본인 몫의 반환액 − 그 반환금에서 의무적으로 상환할 연결 대출 금액. 반환 전에는 현재 현금으로 잡지 않는다.
- 순재원에서 주거·목표 등으로 배정한다. 이미 순재원에서 뺀 상환을 주거 자금 합계에서 다시 빼지 않는다.
- 각 대출 상환 이벤트는 ID로 한 번만 반영한다. 별도 재원에서 상환하는 금액은 별도 유출이며 생략하지 않는다. 한 상환을 여러 재원이 나눠 부담하면 배정 합이 해당 상환액과 같아야 한다.
- 상환액이 반환금보다 크면 음수를 버리지 않는다. 투입 가능액은 0이고, 초과분은 추가로 필요한 상환자금으로 남긴다.
- 동일 자금을 주거·공동 목표·비상금에 중복 배정하지 않는다. 매도된 자산과 매도대금 현금도 동시에 자금원으로 세지 않는다.
- 예정 재원은 `현재 사용 가능 / 본인이 금액·일자를 확인한 예정 / 아직 예상`으로 구별한다. 모두 자기보고이며 지급 보증이 아니다. “예상”은 기본 확보 재원에서 제외하고 별도 시나리오에만 포함한다.
- 납부일별로 그날까지의 누적 필요액과 사용 가능한 배정 재원을 비교한다. 계약금 부족을 나중 잔금 재원으로 지우지 않는다. 여러 납부일의 누적 부족액을 서로 더하지 않는다.
- 필요액 자체가 미정이면 정확한 부족액은 산출 불가다. 일부 재원만 알려졌으면 “현재 입력상 확보한 재원 기준 미충당액”으로 표시하고 전체 자산 부족으로 단정하지 않는다.

예: 본인 보증금 1억 원, 연결 대출 8천만 원이면 반환 후 순재원은 2천만 원이다. 반환이 11월이고 잔금이 10월이면 그 2천만 원은 10월 재원이 아니다. 결과는 “자산이 없습니다”가 아니라 **“돈은 있으나 필요한 날짜에 사용할 수 없습니다”**다.

## 6. ④ 가치관 10문항 + 내 분담안·수용 조건

### 6.1 가치관은 더 늘리지 않는다

10문항·5영역을 유지하되 함께 살기라는 상황에 맞게 문구를 다듬는다. 아래는 **새 버전의 제안 문구**이며 기존 `deep-v2` 문구를 덮어쓰지 않는다. 척도는 왼쪽에 매우 가까움(1) / 조금 가까움(2) / 중간(3) / 오른쪽에 조금 가까움(4) / 매우 가까움(5), 별도 “건너뛰기”다. 3을 모름으로 사용하지 않는다.

| ID / 영역 | 실제 좌우 선택 문구 |
|---|---|
| D1 저축 | 쓰고 남은 돈을 저축한다 ↔ 저축할 돈을 먼저 떼어 둔다 |
| D2 저축 | 목표 금액과 시기를 정해서 모은다 ↔ 상황에 따라 금액과 시기를 조정한다 |
| D3 소비 | 원하는 것이 생기면 빠르게 구매한다 ↔ 충분히 비교하고 고민한 뒤 구매한다 |
| D4 소비 | 경조사·선물에는 넉넉히 쓰고 싶다 ↔ 정한 예산 안에서 최소한으로 쓰고 싶다 |
| D5 투자 | 손실 가능성이 있어도 높은 수익을 추구한다 ↔ 수익이 적더라도 원금 보존을 우선한다 |
| D6 부채 | 필요하면 대출을 활용할 수 있다 ↔ 대출은 최대한 피하고 싶다 |
| D7 공동관리 | 함께 살면 수입과 지출을 통합 관리하고 싶다 ↔ 각자 관리하고 공동비만 분담하고 싶다 |
| D8 공동관리 | 개인 지출 내역까지 서로 공유하고 싶다 ↔ 개인 지출은 각자의 영역으로 두고 싶다 |
| D9 투자 | 여유자금이 생기면 투자할 곳부터 알아본다 ↔ 일단 예적금에 두고 생각한다 |
| D10 부채 | 큰 지출에는 대출을 이용하는 방법도 고려한다 ↔ 지금 가진 돈 안에서 해결한다 |

추가 선택 질문: “이번에 꼭 이야기하고 싶은 영역을 최대 두 개 골라주세요.” 개인 이유 메모는 선택이며 자동으로 상대에게 공개하지 않는다. 역방향은 현재 교정된 D2·D7·D8만 유지하고 D5·D9는 같은 방향으로 둔다. 이를 성격 검사나 과학적으로 검증된 척도라고 부르지 않는다.

### 6.2 성향만으로는 알 수 없는 실제 기준

다음은 D점수에 합산하지 않는 **계획 질문**이다. 본인 의사와 실제 지급 능력도 구별한다. 상대가 얼마를 가졌는지 맞히는 라이트 예측과 다르게, 이번 공동 계획에서 본인이 기대하는 분담을 표현한다.

| ID | 실제 질문 문구 | 답 / 용도 |
|---|---|---|
| C1 | “앞에서 정한 공동비에 본인은 매달 얼마를 내려고 하나요?” | 월 금액 / 미정 / 비공개. 공동비 범위가 미정이면 금액 확정 대신 범위 재논의 |
| C2 | “같은 공동비에 상대가 매달 얼마를 부담하길 기대하나요?” | 선택 금액 / 아직 기대를 정하지 않음 / 비공개. 정답·오답 점수 없음 |
| C3 | “주거 초기자금에는 본인 몫으로 얼마를 투입하려고 하나요?” | ③의 자산 배정 합계를 본인에게 보여주고 확인. 별도 재원처럼 다시 더하지 않음 |
| C4 | “매달 꼭 남겨두고 싶은 개인 돈이 있나요?” | 개인 소비 예산 / 개인 저축·비상금 적립을 구분해 각각 선택 금액. 기존 지출에 포함된 금액을 다시 차감하지 않음 |
| C5 | “이 계획에서 바꾸기 어려운 조건이 있나요?” | 없음 / 월 주거비 상한 / 대출 사용 여부·월 상환 한계 / 개인비 / 주거 조건 / 기타. 중요한 2개부터 작성하되 추가 조건도 보존. 각각 필수 조건인지 선호인지 표시 |
| C6 | “이 분담 방식이나 조건을 두 분이 이미 이야기했나요?” | 내 생각만 정함 / 이야기 중 / 합의했다고 생각함. 마지막 답도 상대 확인을 대신하지 않음 |

조건은 공통 계획에 대한 제약인지 본인의 부담에 대한 제약인지 범위를 명시한다. 기타 짧은 문장은 설명용이며 자연어에서 금액·금지 조건을 자동 추출해 판정하지 않는다. 계산에 쓰려면 구조화된 값을 다시 확인받는다.

분담 여력을 별도로 계산하려면 새 예산에서 **개인 지출과 공동 지출의 범위가 먼저 분리**돼야 한다. 소득·개인비·개인 부채 상환·개인 적립 목표를 모르면 “낼 수 없다”고 결론내리지 않는다. 희망 기여액이 크다는 사실만으로 지급 능력을 확인했다고 표시하지도 않는다.

이를 위해 “현재 지출 중 앞으로 공동비에서 낼 항목과 개인비로 남길 항목은 무엇인가요?”를 조건부로 묻는다. 공동 항목은 P8의 예산에 한 번, 개인 항목은 각자의 미래 예산에 한 번만 둔다. 분류되지 않은 금액이 있으면 합산 기준의 참고 계산과 개인별 분담 여력의 계산 가능 여부를 구별한다. 시스템이 남은 생활비를 임의로 반반 나누지 않는다.

## 7. ⑤ 제출과 공동 공개: 솔직함을 강요하지 않는 잠금

- 로그인은 필수이며 일반 사용자는 카카오, 심사 체험은 별도 A/B 인증 경로를 유지한다. 이번 설계로 실카카오 연결·운영 계정을 새로 활성화하지 않는다.
- 제출 전에 “상대와 함께 볼 내용”을 본인에게 미리 보여준다. 상대 입력이나 공동 계산을 미리 보여주는 것은 아니다.
- 두 사람 모두 제출하고 같은 공동 계획 버전을 확인해야 결과를 연다. 대기 화면은 완료 여부만 보여준다.
- 기존 재무·가치관 공개 동의를 분리한다. 새로운 재원·분담 의사·기대·수용 조건은 **재무 공개 범위**에 명시하고 새 동의 버전을 받는다. 기존 동의로 자동 공개하지 않는다.
- 한쪽이라도 재무 공개에 동의하지 않으면 재무 및 계획 입력에서 파생되는 부족액·조건 충돌·분담 카드도 생성하지 않는다. 가치관은 양측 가치관 동의가 있으면 별도로 제공할 수 있다.
- “이 질문에서 이런 답을 했다”가 노출되는 혼합 카드에는 사용한 모든 영역의 양측 동의가 필요하다. D7·D8 답은 서비스 공개 동의를 대체하지 않는다.
- 공유 불가 화면에는 누가 어떤 금액을 비공개로 했는지 드러내지 않는다. 필요한 입력 안내는 본인의 입력 화면에서만 구체적으로 한다.
- 개인 메모는 계속 비공개다. 공동 제안문은 별도 공유 입력란에 본인이 직접 작성·확인할 때만 공개한다. 이전 비공개 메모를 자동으로 옮기지 않는다.

문구: “공유되지 않은 정보는 추정하지 않습니다. 계산할 수 없는 항목이 있어도 공개된 범위에서 대화를 시작할 수 있습니다.” 공개 철회 후 서버 조회는 차단하되 상대가 이미 본 내용을 회수할 수 없다는 안내를 유지한다.

## 8. ⑥ 결과 판정: 네 가지를 섞지 않는다

아래 상태는 사람의 위험등급이 아니다. 하나의 계획에도 여러 상태가 동시에 존재할 수 있다.

| 구분 | 필요한 근거 | 결과 문구 예시 |
|---|---|---|
| 계산상 부족 | 같은 기준일·범위의 필요한 돈과 알려진 재원·현금흐름 | “잔금일까지 필요한 5,300만 원 중 입력상 확보한 재원은 3,000만 원입니다. 2,300만 원의 조달 방법이 필요합니다.” |
| 미확정 | 금액·날짜·재원 상태가 아직 불명확 | “보증금 반환 날짜가 미정이라 잔금일 재원으로 확정해 넣지 않았습니다.” |
| 의견 차이 | 양쪽 의사·기대·조건의 명시적 차이 | “A는 B의 월 분담을 120만 원으로 기대했고, B는 본인 분담을 80만 원으로 제시했습니다.” |
| 미합의 | 공동 규칙이 없거나 동일 버전의 구체안에 양측 확인이 없음 | “월 분담액 제안이 있지만 두 사람 모두의 확인은 아직 없습니다.” |

**성향 차이 ≠ 미합의.** 통장 관리 취향이 달라도 공동비 전용 통장에 이미 합의했다면 취향만 다르다고 표시한다. 반대로 가치관 답이 같아도 구체적인 분담안을 확인하지 않았다면 “운영 기준 미정”이다. 미응답이나 침묵은 반대나 동의로 해석하지 않는다.

### 8.1 추가로 계산할 세 가지 빈칸

1. **공동비 분담 공백** = 공동비 목표액 − 각자의 제시 분담액 합계. 양수만 공백으로 표시하되 음수는 남는 분담금의 용도가 미정임을 안내한다. 예산 200만 원, 각자 80만 원이면 공백 40만 원이다. 이는 “두 사람에게 돈이 없다”는 뜻이 아니다.
2. **기대 차이** = A가 기대한 B 분담과 B가 제시한 본인 분담의 차이, 반대 방향도 별도 표시. 두 차이를 자금 부족액에 합산하지 않는다.
3. **조건과 계획의 충돌** = 사용자 스스로 정한 범위를 벗어난 구체 계획. “월 주거비 최대 90만 원”에 계획 120만 원이면 30만 원 초과. 대출 거부라는 D6 성향만으로 새 대출안을 금지하지 않고 C5의 명시적 조건을 확인한다.

### 8.2 계산 안전선

- 새 버전의 기본 월 계산은 변동비 절감 가정 없이 현재 입력 합계(계수 1.0)에서 시작한다. 별도로 합의한 미래 항목별 예산이 있으면 그 값을 사용한다.
- 기존 0.85는 “변동비가 15% 줄어든다고 가정하면”이라는 선택 시나리오로만 남긴다. 실제 절감이나 확정 여유자금으로 쓰지 않는다. 입력한 항목별 절감에 또 곱하지 않는다.
- 공동계좌로 보내는 분담금은 내부 이동이지 추가 지출이 아니다. 공동비를 전체 생활비에 두 번 더하지 않는다. 합산소득만으로 공동비가 채워졌다고도 보지 않는다.
- 월 여유자금과 초기자금 부족은 각각 표시한다. “월 저축 가능”이 “지금 입주 가능”을 뜻하지 않는다. 월별 누적 여유자금을 초기 지출 반영 후 순자산이라고 부르지 않는다.
- 공동 목표 적립액과 개인이 남기려는 돈은 기존 지출·배정액과 중복되지 않게 분류한다. 목표 달성 가능성은 목표일까지 사용 가능한 재원과 명시한 적립을 기준으로만 설명한다.
- 실제 월 상환액과 미래 상환 추정을 구분한다. 일부 상환·만기 도래 후 비용을 모르면 해당 미래 구간을 완성된 예산으로 표시하지 않는다.
- 미정·비공개·누락을 0으로 채우지 않는다. 상여·지원·신규 대출을 받을 것으로 임의 가정하지 않는다. 외부 통계로 빈 재무값을 대신 채우지 않는다.

## 9. ⑦ 질문을 대화로 바꾸는 카드

모든 계산 이슈는 결과 목록에서 확인할 수 있어야 한다. **“지금 이야기할 카드 최대 3개” 때문에 네 번째 자금 부족이나 만기 상환을 숨기지 않는다.** 상단에 요약·전체 목록, 아래에 최대 3개 시작 카드를 둔다.

시작 카드 선택 순서는 제품 규칙으로 공개한다. ① 납부일 자금·월 적자 → ② 계산을 막는 미확정 조건 → ③ 분담 공백·명시적 수용 조건 충돌 → ④ 아직 정하지 않은 공동 기준 → ⑤ 가치관 차이. 같은 순위는 필요한 날짜가 빠른 것, 다음으로 사용자가 중요하다고 한 주제, 마지막 고정 ID 순이다. 필수 정보가 부족한 항목은 정확한 부족액 카드 대신 미확정 카드가 된다. 이것은 통계적 위험순위가 아니다.

| 트리거 | 실제 후속 질문 | 제시할 시작 선택지 / 기록 |
|---|---|---|
| 초기자금 부족 | “2,300만 원을 더 마련하는 방법과 주거 계획을 바꾸는 방법 중 무엇을 먼저 검토할까요?” | 보증금·매매 예산 낮추기 / 시작일 조정 / 확인된 추가 재원 입력 / 결정을 보류. 대출 자동 추천 없음 |
| 보증금이 늦게 돌아옴 | “잔금 전에 이 돈을 쓸 수 없습니다. 지급일을 조정할 수 있나요, 다른 재원이 필요한가요?” | 지급일·반환일 확인 담당자와 확인 기한. 법률·반환 보장 판단 없음 |
| 월 현금흐름 적자 | “현재 계획대로면 매달 30만 원이 모자랍니다. 어느 비용이나 조건을 바꿀 수 있나요?” | 항목별 예산 수정 / 주거 조건 재검토 / 실제 소득 정보 수정 / 보류. 근거 없는 소득 증가 가정 없음 |
| 분담 공백 | “공동비 200만 원 중 40만 원의 부담 주체가 정해지지 않았습니다. 누가 얼마를 조정할까요?” | A/B 제안 금액 수정 / 공동비 범위·목표액 조정 / 보류 |
| 기대 차이 | “A가 기대한 금액과 B가 제시한 금액은 40만 원 다릅니다. 같은 공동비 범위를 생각했나요?” | 범위 확인 → 금액 또는 분담 방식 제안. 상대 예측 점수 없음 |
| 수용 조건 충돌 | “현재 월 주거비는 입력한 상한보다 30만 원 높습니다. 주거 계획과 상한 중 조정 가능한 것은 무엇인가요?” | 비용 변경 / 조건 변경 / 둘 다 유지하고 미해결로 기록 |
| 저축 기준 차이 | “이번 목표를 위해 매달 얼마를 먼저 떼어둘까요? 못 지킨 달에는 무엇을 조정하나요?” | 목표액·각자 몫·예외 조건·재논의일 |
| 소비 기준 차이 | “경조사비는 개인비와 공동비 중 어디서 낼까요? 얼마부터 먼저 상의할까요?” | 비용 범주·금액 기준·예외 |
| 투자 기준 차이 | “함께 쓸 돈 중 손실을 감수해도 되는 돈이 있나요? 없다면 공동 목표자금은 어떻게 구분할까요?” | 공동자금의 목적·사용 시점·상의할 범위. 상품·수익률 추천 없음 |
| 대출 기준 차이 | “어떤 목적의 대출까지 함께 검토할 수 있나요? 매달 상환액의 한계는 얼마인가요?” | 목적·범위·한계·미정. 대출 승인액 산출 아님 |
| 공동관리 기준 차이 | “공동비는 어떻게 모으고, 개인 돈은 어디까지 공유할까요?” | 공동비 통장 / 분담 방식 / 공유 범위 / 시험 운영 종료일 |
| 차이가 없음 | “답이 비슷해도 운영 규칙은 별개입니다. 누가 얼마를 언제 내고, 예외는 어떻게 할까요?” | 갈등을 만들지 않고 아직 없는 기준만 기록 |

대안 비교는 사용자 입력을 바꾼 별도 시나리오다. 기준안의 숫자와 나란히 보여주고 초기자금 공백·월 여유자금·목표 적립 부족·미확정 가정을 함께 표시한다. 예를 들어 보증금 2천만 원을 줄여도 월세가 얼마로 바뀌는지 모르면 “초기자금 공백만 비교 가능”이라고 표시한다. 월세·금리·대출 한도를 시스템이 만들어 넣지 않는다.

상호 제출로 잠긴 기본 입력은 시나리오 때문에 수정되지 않는다. 새 조건을 채택하려면 새 공동 계획/라운드에서 양측 확인·동의를 다시 받는다. 합의문 확인만으로 기본 리포트 계산을 덮어쓰지 않는다.

## 10. ⑧ 최종 산출물: 우리 돈의 기준표

리포트는 다음 순서로 끝난다.

1. **지금 계획의 숫자**: 주거 초기자금, 날짜별 조달 공백, 월 예산, 선택 목표. 확정·추정·계산 불가 표시.
2. **아직 비어 있는 부분**: 미확정 재원, 분담 공백, 수용 조건 충돌, 미합의 항목. 심리 점수나 커플 등급 없음.
3. **대화 시작 카드**: 최대 3개와 전체 이슈 목록 링크.
4. **우리 기준표**: 기준명 / 구체 금액·범위 / 담당 / 적용 시점 / 예외 / 재확인 조건·날짜 / 양쪽 확인 상태.
5. **다음 할 일**: 누가 무엇을 언제까지 확인할지. 앱 알림·자동 발송은 이번 범위에 포함하지 않음.

예시 기준표 문장:

> “공동 생활비는 매달 200만 원. A와 B가 각각 100만 원을 매월 25일까지 낸다. 경조사비는 개인비로 둔다. 이 기준은 10월부터 적용하고 11월 말 실제 지출을 보고 다시 정한다.”

확인 상태는 기존 `proposed / agreed / deferred`를 유지하되, 화면에서는 **제안됨 / 둘 다 확인 / 보류**로 쓴다. 아무 제안이 없는 항목은 “아직 정하지 않음”이다. 양쪽이 같은 내용·버전을 확인한 경우만 agreed다. 금액·범위·날짜·예외를 고치면 양측 확인을 초기화한다.

한쪽의 보류는 “한쪽이 재논의를 요청함”이지 둘이 보류에 동의했다는 뜻이 아니다. 다음 점검일이 미정인 보류도 허용하고 그 사실을 표시한다. 합의 완료를 서비스 종료의 강제 조건으로 삼지 않는다. 확인은 실제 송금·계약 이행·법적 서명을 증명하지 않는다.

### 실제 전체 결과 예시 — 합성 입력, 새 설계 기준

소득 합계 월 550만 원, 비주거 고정비 50만 원, 변동비 170만 원, 새 주거 운영비 100만 원, 부채 상환 0원. 사용자가 추가 절감을 가정하지 않았다. 초기 필요액 5,300만 원, 기한 내 배정 재원 3,000만 원. 공동비 목표 200만 원은 이 생활비의 일부이며, 각자 제안 분담은 80만 원이다.

> **“매달 남을 돈과, 지금 필요한 돈은 다릅니다.”**
>
> “입력 기준 월 여유자금은 230만 원입니다. 하지만 주거 초기자금은 2,300만 원 부족합니다. 월 예산이 남는다는 이유로 현재 주거 계획의 자금 문제가 해결되지는 않습니다.”
>
> “또한 공동비 200만 원에 대해 두 분이 제시한 분담액은 합계 160만 원입니다. 나머지 40만 원의 부담 주체가 정해지지 않았습니다. 이는 소득 부족과 별개의 문제입니다.”
>
> “먼저 주거 자금 조달 방법을 정하고, 이어서 월 분담안을 확인해 주세요.”

목표 1,200만 원을 12개월 동안 모으는 입력이 있으면 “월 100만 원 적립 필요”를 따로 표시한다. 초기자금 부족을 해결하지 않은 상태에서 목표 계산만으로 전체 계획을 실행 가능하다고 표시하지 않는다.

## 11. 데이터·구현 경계

기존 기능은 재사용하되, 추가 질문이 저장 없이 장식으로 끝나지 않게 한다. 아래 이름은 신규 설계를 설명하기 위한 논리명이며 **아직 OpenAPI 필드명이 아니다.**

| 묶음 | 현재 재사용 가능 | 새로 필요한 것 |
|---|---|---|
| 개인 재무 | 소득·지출·자산 종류·부채 잔액·월 상환액, known/unknown/withheld | 소득 평균 기준기간, 자산 본인 지분·공동 항목 식별 |
| 자금 투입 | 자산별 `availableOn`, 주거/목표 배정액, 부채 keep/settle | `fundingSources`, 재원 확정 정도, 보증금↔대출 연결, 상환 이벤트, 일부 상환 후 비용 |
| 공동 계획 | 시작월·주거 방식·월 주거비·초기비용·목표 | `fundingDeadlines`, 공동비 범위·항목 예산, 계획 미정 상태 |
| 가치관 | D1~D10·중요 주제·비공개 메모 | 새 질문 카피 버전. 기존 문항 수 확대는 하지 않음 |
| 실행 의사 | 없음 | `contributionIntentions`, 선택적 `partnerExpectations`, `constraints`, 개인비/적립 구분 |
| 결과 | 현금흐름·주거 공백·목표·가치관·최대3개 주제 | 날짜별 재원표, 이슈 유형, 분담 공백, 조건 충돌, 전체 이슈 목록 |
| 공동 결정 | 제안·수정·양측 확인·보류와 버전 | `decisionTerms`의 금액·범위·역할·시점·예외, 제안 출처 리포트 버전 |
| 비교 | 계산 엔진 재사용 가능 | 기준안을 변경하지 않는 시나리오 입력·결과 경계 |

승인 뒤의 구현 묶음은 다음 순서로 나눈다. 한 번에 모든 화면·API를 변경하지 않는다.

1. **재원 정확도**: 연결 대출·반환일·납부일·재원 상태, 순재원과 이중 차감 방지, 직접적인 부족액 카피.
2. **공동 기준**: 공동비 범위·본인 분담·상대 기대·수용 조건, 네 종류의 이슈, 구조화된 양측 확인.
3. **흐름 완결**: 조건부 질문 카탈로그, 전체 결과·상위3카드, 별도 대안 비교, 프론트 전달 fixture·OpenAPI.

각 묶음은 별도의 실행 계획과 검증을 거친다. 이 문서는 제품 최종 흐름이며 개별 함수·마이그레이션 절차를 지시하는 실행 계획이 아니다.

새 세션에 `deep-v3` 계열 질문·규칙·카피·동의 버전을 고정하는 안으로 잡는다. 실제 버전 문자열은 계약 확정 시 정한다. 기존 `deep-v2`의 문항 방향·0.85 산식·제출 입력·리포트·동의는 소급 변경하지 않는다. 구버전 소비자가 신필드를 모르는 동안 신버전으로 자동 전환하지 않는다. 계획 변경·확인 동시 요청·오래된 revision은 기존 충돌 보호를 확장한다.

### 별도 후속 범위 — 영구 제외가 아니다

- 소득 감소·일시 실직 같은 스트레스 시나리오는 기본 재원·분담 흐름을 검증한 뒤 추가한다. 기간·감소액·지출 유지 조건·사용 가능한 비상금을 사용자가 정해야 하며 위험 점수로 바꾸지 않는다.
- AI 해설은 이번 설계의 의존성이 아니다. 후속으로 양측 추가 동의 아래 공개 가능한 계산 근거·선택된 이슈만 설명하게 한다. 모델이 숫자·합의 여부를 판정하지 않고 실패하면 템플릿으로 완료한다.
- 정책 매칭은 최신 정책 데이터와 자격 근거 검증 후 별도 구현한다. 이를 위해 지금 불필요한 신상정보를 미리 수집하지 않는다.
- 숫자형 Say-Do·고정 16개 유형 해설은 별도 타당성·문구 검토 전까지 보류한다. 첨부 파라미터의 통계 앵커·경고 임계값을 이번 추가 질문의 점수로 전용하지 않는다.

## 12. 승인 후 확인할 수용 사례

1. 보증금 1억·연결 대출 8천만 원·기한 내 반환·전액 투입이면 주거 재원은 2천만 원. 순자산과 별도로 보이고 상환은 한 번만 차감한다.
2. 같은 보증금의 반환일이 잔금 뒤라면 잔금일 재원은 0원. 반환 이후 날짜에는 반영하며 “자산 없음”으로 표시하지 않는다.
3. 보증금보다 연결 상환액이 크면 초과 상환자금이 남는다. 0으로 잘라 문제를 지우지 않는다.
4. 하나의 상환 이벤트를 자산 연결·부채 정리 양쪽으로 입력해도 중복 차감하지 않는다. 나눠 갚으면 배정합을 검증한다.
5. 계약금 기한에는 재원이 없고 잔금 때는 충분한 경우 계약금 공백이 사라지지 않는다. 누적 부족액들을 합산하지 않는다.
6. 이미 자산에 들어온 지원금·매도대금이 추가 재원으로 이중 계산되지 않는다. 예상 지원은 기본 확보 재원에서 빠지고 가정 시나리오에서만 반영된다.
7. 공동예산 200만·각자 분담 80만이면 공백 40만. 합산소득이 충분해도 분담 공백은 남고 지급 능력 부족으로 부르지 않는다.
8. A가 B에게 기대한 120만·B 본인 제안 80만이면 기대 차이 40만. 실제 자금 부족액에 더하지 않는다. C2 미응답은 기대 0원이 아니다.
9. 공동계좌 분담금과 그 계좌로 내는 생활비를 현금흐름에서 이중 차감하지 않는다. 이미 포함된 개인비도 재차 차감하지 않는다.
10. 가치관이 달라도 동일한 운영안에 양측 확인이 있으면 그 기준은 합의됨이다. 가치관이 같아도 제안 확인이 없으면 미정이다.
11. 월 주거비 상한이 선호인지 필수 조건인지 구별한다. 자유메모와 D6만으로 숫자 상한이나 대출 금지를 만들어내지 않는다.
12. 월 여유자금이 양수여도 초기자금이 부족하면 두 사실을 동시에 표시한다. 목표 적립 가능이 초기자금 문제를 감추지 않는다.
13. 새 기본안은 절감 가정 1.0이다. 선택한 0.85 비교에는 가정 표시가 있고 이미 합가한 실제 지출이나 항목별 수정 예산에 중복 적용하지 않는다.
14. 재무 공개가 거부되면 분담·조건·재원 파생 카드도 없다. 상대의 입력 내용에 따라 사전 질문·대기 응답이 달라지지 않는다.
15. 차이가 없으면 갈등 카드를 만들지 않는다. 이슈가 4개 이상이면 시작 카드는 3개여도 나머지 자금·상환 이슈가 전체 목록에 남는다.
16. 기준표 내용 변경 시 양측 확인이 초기화된다. 한쪽의 “이미 합의했다” 응답이나 보류로 공동 확인이 성립하지 않는다.
17. 시나리오 비교는 원본 입력·보고서·합의를 바꾸지 않는다. 채택 후 새 라운드에서 다시 확인한다. 구버전 세션 출력은 새 질문 배포로 변하지 않는다.
18. 부분 상환 후 월 비용·재원 날짜 등 핵심 입력이 없으면 해당 계산만 partial/unavailable이고, 가능한 다른 계산·대화는 계속 제공한다.
19. 재로그인·자동저장 충돌·동시 제출·동의 철회·만료·심사방 초기화에서 기존 멤버십과 비공개 보호가 유지된다. Light 계약에 회귀가 없어야 한다.
20. AI·정책 API 없이 두 계정이 질문→동의→결과→구체 제안→양측 확인/보류까지 완료할 수 있다.
